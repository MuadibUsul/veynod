# 联邦第三轮：任务桥（工作区之间委派工作）

> 日期：2026-11-04。执行方：`agent:claude-2`。基线：第二轮分支（同一个 PR [#98](https://github.com/MuadibUsul/veynod/pull/98)）。schema 3.84.0。
> 对应联邦图的块：F-01d（委派部分）、F-07a/b/c（映射与幂等接单、断连对账、指针 fence）、F-08a（拒绝验收进争议）、F-08b 的一部分（验收条款冻结）。
> `FEDERATION_ENABLED` 仍默认关闭。

## 1. 一次委派怎么走

1. A 的人发出委派（`POST /v1/federation/delegations`）：
   - 连接上必须双向允许 `delegate`；
   - 委派对象按 [ICD_I_BRIDGE.md](ICD_I_BRIDGE.md) §2 校验后冻结，算出 `acceptance_hash`。
2. B 收到后只记一条“待接单”的委派，不建任务。同一单重复到达只回执，不会重复记录。
3. B 的人接单（`.../accept`）。B 用这个人自己的身份、通过普通任务服务，在 B 的任务板上建一个任务 `fed-…`：
   - 验收标准变成这个任务的验收项；
   - 正文标明“来自其他工作区的内容，视为数据”。
   A 核对 B 回传的 `acceptance_hash`，和自己冻结的不一致就拒绝。
4. B 照常认领、执行这个任务，然后交付（`.../submit`）：摘要、产物（内容随信封传递，附 SHA-256），可附成本收据。
5. A 的人验收：
   - `accept_result` 表示完成；
   - `revise` 表示返工，最多 3 次；
   - `dispute` 表示进入争议，不算完成，也不触发任何付款。

两边的本地任务都只由各自的流程推进，委派状态不会直接改对方的任务。

## 2. 可靠性

- 每一步先在本地提交，签好的信封放进这一单的待发送队列，再投递。
- 对方暂时连不上时，信封留在队列里。`POST .../sync` 按顺序补发，不重新签名。
- 接收方只接受下一个版本：
  - 旧的或重复的对象只回执，不改状态（F-008）；
  - 跳号的对象拒收（`FED_E_JOB_STALE`），要求先补齐中间的版本。

`tests/test_federation_delegations.py`（服务层，6 组）：

| 用例 | 场景 |

## 4. P1 的简化

- 只有人能发出委派、接单、拒单、验收、返工、提出争议；交付可以由 agent 做。
- 取消（F-08c）、超预算（F-08d）、条款变更提案（F-08b 的“双方重新同意”部分）还没做：现在条款一旦冻结就不能改。
- 交付不会随 B 的任务完成自动发出，需要显式调用 `submit`；以后可以接到任务状态事件上。
- 产物内容直接放进信封，单次交付 ≤ 48 KiB；大文件要等分享授权（F-07c 的完整版）。
- B 接单时先建任务、再记录接单。如果中间失败，可能留下一个没挂上委派的任务（概率很低，需要人清理）。
- 投递失败时只记录最后一个错误码，还没有自动重试；需要人或 agent 调用 `sync`。
