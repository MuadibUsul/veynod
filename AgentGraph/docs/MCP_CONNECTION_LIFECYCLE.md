# MCP Connection Lifecycle

**Status:** Rollout steps 1–3 implemented (schema 3.100.0, CLI 0.9.0), not yet released; steps 4 (console) and 5 (OAuth) are open  
**Date:** 2026-10-25, implementation notes 2026-11-11  
**Scope:** `npx veynod init`, MCP clients, agent-token lifecycle, console Agents page

## 1. Problem

Today an agent token is treated as both the connection identity and the secret.
MCP clients (Cursor, Claude Code, Claude Desktop) have no reliable "disconnect"
callback, so when a user removes an MCP entry the platform keeps the token row
forever. Running `npx veynod init` again mints another token whose signature is
suffixed to avoid the unique `(workspace_id, agent_signature)` constraint:

```text
cursor, cursor-2, cursor-3, ...
```

The result is a growing list of indistinguishable credentials, many already
revoked or unused. A token is a credential, not a connection; the current model
cannot express "this is the same client reconnecting".

## 2. Goals

- One stable connection identity per MCP client installation and workspace.
- Reconnecting rotates the existing credential instead of minting a new token.
- Tokens expire by default; deleting a client configuration eventually removes
  its access without depending on a client-side disconnect event.
- The console shows active connections by default; expired and revoked
  credentials are history, not a second list of agents.
- Preserve the audit trail: revoke credentials, never hard-delete them as part
  of normal lifecycle cleanup.

## 3. Non-goals

- Detecting the exact moment a local MCP process exits. MCP over stdio has no
  reliable lifecycle notification to the server.
- Merging two different machines into one connection just because they share a
  hostname or client kind.
- Changing the existing `agent_tokens` authorization semantics, RLS, lease or
  grant-snapshot behavior.

## 4. Concepts

### Connection

A long-lived installation identity:

- one workspace;
- one `client_instance_id` generated by the client;
- display label and client kind(s);
- status: `active`, `dormant`, `revoked`;
- `last_seen_at`.

### Credential

The secret presented to `/mcp/` (an `agent_tokens` row):

- points at a connection;
- has a TTL (`expires_at`);
- can be rotated (the previous secret has a short grace window);
- is revoked, never deleted, on expiry or disconnect cleanup.

One connection has one active credential and many historical credentials.
The connection is what the console lists; credentials are its history.

## 5. Data model

Migration `v3_38_mcp_connections.sql`:

```sql
CREATE TABLE mcp_connections (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    workspace_id UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    tenant_id VARCHAR(40) NOT NULL,
    client_instance_id VARCHAR(64) NOT NULL,
    client_kind VARCHAR(32) NOT NULL DEFAULT 'other',
    label VARCHAR(64) NOT NULL DEFAULT '',
    status VARCHAR(16) NOT NULL DEFAULT 'active'
        CHECK (status IN ('active', 'dormant', 'revoked')),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    last_seen_at TIMESTAMPTZ,
    revoked_at TIMESTAMPTZ,
    UNIQUE (workspace_id, client_instance_id)
);

ALTER TABLE agent_tokens
    ADD COLUMN connection_id UUID REFERENCES mcp_connections(id) ON DELETE SET NULL;
CREATE INDEX idx_agent_tokens_connection
    ON agent_tokens (connection_id) WHERE connection_id IS NOT NULL;

ALTER TABLE cli_sessions ADD COLUMN client_instance_id VARCHAR(64);
```

`mcp_connections` is workspace-scoped and follows the same tenant trigger,
forced RLS policy and `agentgraph_app` grants as `support_access_grants`.

Legacy tokens keep `connection_id = NULL`; they remain visible as legacy
entries and can be adopted the next time a matching signature reconnects.

## 6. Lifecycle

### 6.1 First connection

1. `npx veynod init` generates a `client_instance_id` (UUIDv4) and stores it in
   `~/.veynod/connection.json` with mode 0600.
2. It sends the ID in `POST /v1/auth/cli/sessions`.
3. On approval the server upserts a connection for
   `(workspace_id, client_instance_id)`, creates one credential linked to it,
   and gives the credential a TTL.
4. The CLI seals the credential to its terminal key and writes the MCP config.

### 6.2 Reconnect (same machine)

1. The CLI reads the same `client_instance_id`.
2. Approval finds the connection and its active credential, updates the grant
   (role/namespaces) and extends the TTL.
3. The server rotates the credential secret in place: same token row, same
   `agent_signature`, new secret; the previous secret keeps the existing
   hot-swap grace window.
4. The CLI rewrites the MCP config with the new secret. No `cursor-2` appears.

If the connection exists but its credential was revoked, a new credential is
issued for the same connection and signature.

### 6.3 Legacy token adoption

If no connection exists, but an active token with the requested
`agent_signature` exists and has no `connection_id`, the approval links that
token to the new connection and rotates it. This upgrades existing installs
without creating duplicates.

If the signature belongs to a different connection, fall back to the existing
unique-name behavior rather than stealing another connection's credential.

### 6.4 Client configuration deleted

The platform cannot know immediately. The credential TTL is the cleanup
mechanism:

- default credential TTL: **90 days**;
- `npx veynod init` reconnect extends the TTL;
- expired credentials are marked revoked by the reaper and stop working;
- the connection is marked `dormant` after **60 days** without use and may be
  revoked after **90 days**;
- a later reinstall without the old state file creates a new connection, while
  the old one is already dormant/revoked.

No client-side "remove MCP" callback is required.

### 6.5 Revocation

`veynod disconnect`, the console, or an admin action revokes the connection:
all active credentials are revoked immediately, and the connection status
becomes `revoked`. Audit rows and grant snapshots remain.

## 7. API changes

### CLI device flow

`CliSessionCreateRequest` gains:

```json
{
  "client_instance_id": "uuid",
  "client_label": "hostname",
  "clients": ["cursor"]
}
```

`client_instance_id` is optional for older CLIs. Without it, behavior stays
today's (mint a unique signature).

Approval uses the session's `client_instance_id` and does not add a new public
parameter. The approval response should include the connection ID and whether
the credential was created or rotated.

### Token output

`AgentTokenOut` adds:

- `connection_id`
- `connection_label`
- `connection_status`

### Connection APIs

- `GET /v1/human/connections` — owner/admin view, active by default;
- `POST /v1/human/connections/{id}/revoke` — revoke connection + credentials;
- `GET /v1/admin/workspaces/{id}/connections` — operator counts only unless
  support access is open;
- `POST /v1/human/connections/{id}/rotate` — optional explicit rotation.

All endpoints are workspace-scoped and audited.

## 8. CLI changes

Add a small local state file:

```json
{
  "client_instance_id": "...",
  "host": "https://veynod.com",
  "created_at": "..."
}
```

Location: `~/.veynod/connection.json` (0600). It is independent of any MCP
client's config so it survives MCP config rewrites.

Commands/options:

- `npx veynod init` — read the state file, otherwise create it;
- `--fresh` — force a new connection ID (old one will expire);
- `--client-instance-id <id> — advanced/CI use;
- `npx veynod disconnect` — revoke the connection via an owner-approved flow;
- The existing `--client`/`--host`/`--no-open` behavior is unchanged.

The CLI must never print the raw credential unless `--client print` is used,
and the state file must never be committed.

## 9. Console changes

Agents page:

- list **connections**, not every token;
- one row shows display label, client kind, role, namespaces, last seen,
  connection status and active credential count;
- credentials fold under the connection, default collapsed;
- revoked/expired credentials are hidden by default behind
  “Show inactive”;
- “Reconnect” rotates the credential without changing the connection identity;
- “Revoke” revokes the connection and all credentials;
- legacy tokens without a connection still appear in a “Legacy” group until
  adopted or revoked.

Onboarding progress and directory entries attach to the active credential /
connection, so a reconnect does not reset onboarding.

## 10. Reaper and cleanup

On each existing reaper iteration:

1. Revoke active tokens with `expires_at < now()`:
   `is_active = false`, `revoked_at = now()`,
   `revoke_reason = 'expired'`.
2. Mark connections dormant when no credential was used for 60 days.
   Use `agent_directory.last_seen_at` or the latest access-log timestamp, not
   `agent_tokens.last_seen_at` alone.
3. Revoke dormant connections after 90 days.
4. Keep revoked rows for audit; do not hard-delete them in normal operation.
5. Optional retention job: after 180 days, delete only historical credential
   metadata that is no longer referenced by grant snapshots.

## 11. Security and audit

- Raw credentials are never stored; only hashes.
- `rotate` uses the existing hot-swap behavior: previous secret valid for a
  short grace window.
- Connection revocation is audited with actor, workspace, connection ID and
  reason.
- Cross-workspace connections are separate even with the same
  `client_instance_id`.
- RLS: connection rows are visible only inside their workspace; operators see
  counts under the operator-privacy rules.
- The CLI state file is mode 0600 and contains no raw credential (only the
  connection ID); the credential stays in the MCP client's secure config.

## 12. Acceptance criteria

1. Running `npx veynod init` twice on the same machine and workspace creates
   **one** connection and **one** credential row; the second run rotates the
   secret and keeps the same `agent_signature`.
2. Running it with a different `client_instance_id` creates a second
   connection; different machines are not merged.
3. Deleting the client config and never reconnecting: the credential expires
   and is revoked by the reaper; it no longer authenticates.
4. Reconnecting after a long absence with the same state file rotates the same
   connection; onboarding progress is preserved.
5. A legacy token with the same signature is adopted instead of producing
   `cursor-2`.
6. Revoking a connection immediately invalidates current and previous secrets
   and leaves audit and grant snapshots intact.
7. The Agents page hides revoked credentials by default and shows one
   connection row per installation.
8. No hard delete of normal lifecycle credentials; a restored backup still
   contains the audit trail.
9. Existing API clients that do not send `client_instance_id` keep working.
10. Operator privacy: a private workspace's connection details are content;
    the operator sees counts only unless support access is open.

## 13. Rollout

1. **Schema + read APIs (non-breaking):** add tables/columns; backfill nothing;
   legacy tokens remain nullable. Expose `connection_id` in token output.
2. **CLI idempotency:** ship the state file and `client_instance_id`; approve
   reuses/rotates; keep fallback for older CLIs.
3. **Cleanup:** TTL on CLI tokens, expired-token reaper, dormant status.
4. **Console:** connection grouping, inactive filter, reconnect/revoke actions.
5. **Remote OAuth:** map OAuth dynamic clients to connections; access token
   1 hour, refresh token 30 days, revoke on disconnect.

Steps 1–2 solve the duplicate-token problem; steps 3–4 solve stale records and
visibility; step 5 covers claude.ai-style connectors.

## 14. Decisions to confirm

- Credential TTL: 90 days, extended by reconnect. (Alternative: 30 days for
  higher churn.)
- Dormant threshold: 60 days; revoke at 90 days.
- Connection identity: per workspace + client installation, never by display
  name alone.
- Legacy adoption: only when the signature is unowned; never steal a token
  already linked to another connection.

## 15. As implemented (2026-11-11)

Steps 1–3 of §13 are in the code. What differs from the text above, and why:

- **Migration** is `v3_100_mcp_connections.sql` (3.38 was taken).
- **The expiry slides while the credential is in use.** §6.4 extends the TTL only
  on a reconnect. A computer that runs tasks never signs in again, so its key
  would have stopped after 90 days of daily use. The reaper moves the expiry
  forward for a CLI credential that was used in the last week and is in the
  second half of its life; one nobody uses still runs out. "Used" is the
  agent's directory entry, the computer's runner heartbeat or the connection's
  last sign-in (`agent_tokens.last_seen_at` is not written today).
- **Settings**, with §14's values as defaults, so the owner can change them
  without a release: `CLI_CREDENTIAL_TTL_DAYS=90` (0 turns expiry off),
  `CONNECTION_DORMANT_DAYS=60`, `CONNECTION_REVOKE_DAYS=90`. §14 was not
  confirmed by the owner before implementation; these are the proposal's own
  defaults.
- **Every credential the CLI issues expires**, with or without an installation
  id; only the ones with an id belong to a connection.
- **One state file for all boards**: `~/.veynod/connection.json` holds one id per
  host (`{"hosts": {"https://veynod.com": {"client_instance_id": …}}}`), so the
  same machine on two boards is two connections.
- **Several identities in one sign-in** (`veynod up` asks for the computer and
  its extras) share the connection; each is matched by its `agent_signature`.
- **A revoked connection issues nothing more**: signing in with its id answers
  409 `connection_revoked`; `npx veynod --fresh` starts a new one.
- **Not done**: `veynod disconnect`, `POST …/connections/{id}/rotate`, the
  console's connection grouping (step 4) and OAuth refresh tokens (step 5).
  `purge_stale_delegated()` still hard-deletes long-expired tokens that agents
  delegated (depth 2 and deeper); CLI and console credentials are never deleted.
